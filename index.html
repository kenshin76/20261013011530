1

프로젝트 이해

현재 운영 중인 사이트는 교과서·참고서(textbook), 단행본(books), 수업지원자료실(class) 3개입니다. 과업 A는 교과서·참고서 사이트와 단행본 사이트 2개를 하나의 도메인으로 통합하고, C# 시스템을 Java Spring Boot로 재구축하는 작업입니다. 기존 이용자와 인쇄물 QR의 연결을 유지하면서 OS(Windows → Ubuntu)와 DB 구조(N:M 개편)도 단계적으로 전환합니다. 전환 순서와 문제 발생 시 복귀 절차를 먼저 검증하겠습니다. 통합 사이트에서는 도서·작가·카테고리·자료를 한곳에서 관리하고, 교과서·참고서와 단행본을 통합 검색할 수 있도록 구성하겠습니다. 과업 B는 수업지원자료실을 별도 사이트로 유지하면서, 기존 React·API·서버 환경에서 유지보수·고도화를 수행하는 작업입니다.

아래 항목은 필요하실 때 눌러서 펼쳐 보실 수 있습니다.

2

핵심 수행 방안

펼쳐 보기접기
  1. 01

    기능 목록을 먼저 확정하는 재구축

    C# 코드를 1:1로 옮기지 않고, 화면·컨트롤러·DB 객체(테이블·프로시저·트리거)를 분석해 기능 목록을 만든 뒤 Spring Boot 계층 구조로 재구축합니다. 업무 규칙은 Java 계층에 모으고, 레거시와 신규 화면의 결과(목록 건수·상세 필드·검색 결과)를 자동으로 비교해 빠진 기능이 없는지 확인합니다.

  2. 02

    인쇄된 QR을 정확한 새 주소로 연결하는 301

    현행 주소는 /Home/BookDetail?bookid=…처럼 ID가 쿼리에 들어 있습니다. ALB는 옛 도메인 요청을 새 애플리케이션으로 넘기고, 애플리케이션이 「원본 도메인 + 자료 유형 + 옛 ID → 신규 ID」 대응표로 정확한 새 주소에 301 응답합니다. 과업 A의 두 사이트에 같은 ID가 있어도 서로 다른 책으로 연결됩니다. DB·접속 로그·인쇄물에서 옛 주소를 모아 전수 자동 검증하고 실물 QR도 직접 스캔하며, 확인되지 않은 주소는 임의의 화면으로 보내지 않고 안내와 기록으로 보완합니다.

  3. 03

    두 번에 나눈 전환과 파트너사 협업

    단행본을 먼저 전환해 절차를 다듬은 뒤 교과서·참고서를 전환합니다. 당사가 ALB·인증서·DNS 설정 명세와 검증을 맡고, 파트너사가 승인된 명세대로 적용하는 3자 협업으로 진행합니다. 전환마다 승인된 구성·복귀 조건에서 복귀 결정 후 10분 이내 서비스 경로 복귀를 리허설 목표로 검증합니다. 전환 후 입력 데이터의 보존·재반영·대조와 쓰기 재개 시간은 별도로 확인합니다.

미확정 ① DB 처리 방식신규 스키마 이관을 권장하되, 신규 서버 도입은 별도로 판단합니다. 기존 MySQL 서버의 버전·용량·부하·권한·백업 조건이 맞으면 같은 서버에 신규 스키마를 만들어 추가 DB 서버 비용 없이 운영합니다. 서버 분리가 필요하면 관리형 MySQL·신규 서버 내 MySQL의 실비를 파트너사 견적으로 비교해 G1에서 승인받습니다. 기존 DB 공유안과의 공수 차이 1~2 MD(25~50만원 환산)는 기본 가정 내에서 80 MD 배정을 조정해 흡수합니다
미확정 ② 계약 구조단계별로 나눠 계약하되, 과업 B의 월 투입량·단가·인력·연계 조건을 과업 A 계약 때 미리 합의하기를 권장합니다. 과업 A 결과를 확인하고 B 별도 계약을 확정해 04-01부터 같은 팀이 이어가는 안입니다. 일괄 계약을 원하시면 A·B의 검수·정산 조건을 구분한 합의안도 제시하겠습니다
미확정 ③ 월 리소스 초과 정산월 기본료는 정액이며, 다음 달까지만 이월(최대 4 MD)·다음 달 할당에서 차감하는 선사용(최대 4 MD)·사전 승인 추가 정산(250,000원/MD) 중 해당 방식을 적용합니다. 마지막 달에는 선사용하지 않고 잔여분을 승인된 작업에 배정하며, 종료 후 연장·잔여분 정산은 종료 전 서면 합의합니다 (§5)

착수 전에 함께 정할 주요 사항 — 신규 통합 도메인 이름, 인쇄된 QR 목록과 http/https 여부, DB 객체 규모, 관리자 화면 퍼블리싱 담당, 네이버 클라우드의 네트워크·ALB 연결 조건 (그 밖의 항목을 포함한 12건은 제안서 §3-4에 정리했습니다).
